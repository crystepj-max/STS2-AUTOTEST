## 背景与实测

`STS2-GAWAIN/automation/autotest/lib/spec_gate.py:81-82`：

```python
if suite.suite_assertions:
    reasons.append('套件 Then 尚未实现：当前生成器只输出注释，不能认定已执行这些断言')
```

只要套件写了 `## Then` 就无条件阻断，不看内容、不看能否落地。

实测复算（只读调用 `inspect_specs()`，`.venv` 解释器）：

- `suite_count = 35`，其中**有套件级 `## Then` 的 = 34**；唯一没有的是 `SUITE-GAWAIN-M1-MAGICWEB-RESONANCE`。⇒ **D 类 problem = 34**，占 107 的 31.8%，为单行最大来源。

- 生成侧确认：`core/code_generator.py:421-422` 把 `suite_assertions` 逐条渲染成 `# Suite assertion: {assertion}` **纯注释行**，套件级没有任何 `.assert_that()`。对照：套件内**各用例**的断言走 `:470-473`，确实调 `_assertion_to_call` 并真实执行。⇒ 阻断消息里"只输出注释"的说法**属实**。

## 评估：该不该拆成条件判定

**不该。** 三点依据：

1. **阻断理由与内容无关，条件化就是造假 READY。** D 类不是因为"这句 Then 写得不好"，而是因为"套件级 Then 没有任何执行出口"（`code_generator.py:421-422`）。即便某句恰好能被 `_assertion_to_call` 映射（实测 6 句），它在套件级也**无人调用**——那 6 句同样没被执行。按可映射性放行 ⇒ 6 句从诚实 BLOCKED 变成假 READY，与 LOC-009 修的是同一类缺陷，方向相反。
2. **"条件判定"的合法条件等价于先做上游 REQ-07。** 唯一站得住的条件是"该断言既可映射**且**套件生成码真的把它放进某次 `.assert_that()`"。后半句成立时 REQ-07 已经完成，此时 `:81-82` 整段该删掉而不是加条件。所以本条没有独立可做的工作量。
3. **34/107 的"噪音"是计数口径问题，不是判定错误。** 34 条 problem 其实是**同一个平台缺口**的 34 次实例化。归因正确、判定正确，只是把一件事按套件数量摊开了。
