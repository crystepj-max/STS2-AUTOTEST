# STS2-AUTOTEST 平台能力盘点与边界

本文回答两个问题：

1. STS2-AUTOTEST 已经能为任意 Mod 项目提供哪些通用能力；
2. 哪些能力应继续留在平台，哪些只能由 Gawain 项目测试提供。

判断标准是：一个新 Agent 或一个新 Mod 项目能否只提交“测试目标”，而不需要自己重复处理游戏启动、页面等待、恢复、排队和证据收集。

## 一、平台定位

STS2-AUTOTEST 是“测试任务执行平台”，不是 Gawain 的业务测试代码仓库。

平台负责把测试目标可靠地变成一次可追踪的运行任务：

```text
Agent 提交目标
  → 平台检查环境
  → 独占游戏会话并排队
  → 启动或复用游戏
  → 处理通用过场和页面
  → 执行项目测试
  → 自动恢复异常
  → 固化状态、日志、截图和报告
  → 返回可机器读取的结论
```

项目测试只负责回答“这个 Mod 的功能是否符合预期”，例如角色、卡牌、遗物、数值、文本和专属规则。

## 二、现有能力盘点

| 能力域 | 当前能力 | 复用判断 | 当前边界 |
|---|---|---|---|
| 测试目标入口 | `autotest run`、pytest 插件、MCP 服务、AgentAdapter | 通用 | 多种旧入口并存，统一运行契约已建立，仍需逐步让旧入口全部转到该契约 |
| 游戏控制 | CliModAdapter、AgentAdapter；AgentAdapter 支持 HTTP 和 MCP 两种连接方式 | 通用 | 连接协议属于平台，具体调试命令属于项目扩展 |
| 状态读取 | 主菜单、选角、地图、战斗、事件、商店、营火、宝箱、奖励等状态统一为平台状态 | 通用 | 新游戏版本增加页面时，应先补平台状态映射，不应由每个项目各自猜测 |
| 动作执行 | 动作可用性检查、参数归一化、动作结果读取 | 通用 | “动作返回成功”不等于目标状态已达成，必须继续检查状态变化 |
| 通用导航 | 开局事件、对话、卡包、选牌、奖励、宝箱、休息、商店和地图推进 | 通用 | 默认只做最小推进，不判断项目专属卡牌价值或策略 |
| 新局处理 | 回到主菜单、清理可处理的旧存档、选择角色、开始冒险 | 通用 | 角色标识由项目或 Agent 提供，平台不应固定 Gawain |
| 旧局恢复 | 继续已有对局并确认回到可操作状态 | 通用 | 若旧局已损坏或游戏状态不可退出，进入恢复流程，不把“点击成功”误判为恢复成功 |
| 首战流程 | 从新局推进到第一场真实战斗 | 通用 | 进入战斗后，打哪张项目卡牌属于项目用例 |
| 状态异常识别 | phantom combat、地图旅行无进展、接口不可用等异常检测 | 通用 | 发现异常后要由生命周期管理器执行重启，不能只在单个用例里重试 |
| 恢复 | 快速重连、重建控制连接、重启游戏、必要时重启 Steam | 通用 | 重启后必须重新确认接口可用和游戏可操作，不能只检查进程存在 |
| 断点续跑 | 保存会话进度、失败后使用 `--resume` 继续 | 通用 | 续跑粒度应保持在安全步骤边界，不应从半个不可逆动作中间恢复 |
| 单游戏排队 | 持久化任务记录、先进先出、暂停、取消、任务进程脱离控制端继续运行 | 通用 | 同一机器默认只允许一个游戏任务实际占用游戏会话 |
| 任务可观察性 | `run_id`、阶段、状态、进程、退出码、证据目录和结果 | 通用 | 所有 Agent 都应查询任务状态，不依赖长连接是否仍然存在 |
| 证据 | 状态 JSON、测试报告、截图、日志、失败信息、压缩包 | 通用 | 每个任务必须有唯一证据目录；截图不可用时仍需保留状态和日志，并明确标记截图缺失 |
| 报告 | 机器可读 JSON、JUnit、摘要和 HTML 报告 | 通用 | HTML 是展示层，不能替代任务状态和原始凭证 |
| 自然语言规格 | 规格审查、编译、pytest 执行 | 通用 | 语言解析只负责把项目意图变成用例，不应把 Gawain 规则写入平台导航 |
| 环境检查 | 游戏、Steam、控制接口、目录和登录状态检查 | 通用 | 不满足前置条件必须归类为环境阻塞，而不是项目失败 |
| Test Agent 工作流 | 构建、本地化、部署、启动和冒烟测试流程 | 部分通用 | 流程编排可复用；Mod 项目路径、构建产物和业务断言必须由项目配置提供 |
| Visual QA | 截图健康检查和 OCR 能力 | 通用 | 只能作为证据辅助，不能在没有状态/日志证据时单独宣布通过 |

## 三、必须由平台继续承担的工作

以下事项在过去 Gawain 的 M1-M7 全回归中反复出现，说明它们不是某一个用例的问题，而是平台公共入口的问题。它们必须在平台层一次解决：

### 1. 唯一任务入口

所有 Agent 最终都提交同一种任务请求，得到同一种 `run_id` 和同一套状态。CLI、MCP、pytest 插件和旧脚本可以继续兼容，但不能各自维护一套启动、排队和恢复逻辑。

### 2. 游戏会话独占与任务持久化

控制端退出、网络断开或 Agent 被替换后，测试仍应继续运行。任务记录必须落盘，支持：

- 查询当前阶段和最后一次状态；
- 取消等待中的任务或正在执行的任务；
- 从已保存进度继续；
- 同一请求重试时通过幂等键避免启动两次；
- 游戏会话被其他任务占用时自动排队；
- 机器重启后能够识别消失的工作进程并归类为平台失败。

### 3. 新局、旧局和异常局的生命周期

平台必须把“准备测试环境”作为正式阶段，而不是把它散落在每个 Gawain 用例的第一步：

- 新局：主菜单 → 选角 → 开始冒险 → 开局事件处理 → 稳定地图；
- 旧局：主菜单 → 继续对局 → 处理残留页面 → 稳定地图或战斗；
- 异常局：识别 phantom combat、旅行无进展、接口失联 → 保存证据 → 重启 → 再确认可操作；
- 重启失败：归类为平台失败或环境阻塞，并停止继续消耗测试时间。

### 4. 通用多步骤推进

平台只做“让测试到达目标页面”的动作，不替项目做业务判断。至少要稳定处理：

- 开局事件和对话；
- 卡包选择；
- 多张牌选择和确认；
- 战后奖励领取、跳过和继续；
- 地图节点选择，并确认地图已真正稳定；
- 第一场真实战斗入口。

动作必须满足两个条件才算完成：接口返回成功，且重新读取状态后页面或关键状态发生了预期变化。

### 5. 默认证据

平台默认采集证据。项目用例不应自己决定什么时候截图、如何保存日志、如何压缩报告。最低要求是：

- 任务记录；
- 最终状态；
- 每个失败步骤的错误信息；
- 失败时的状态快照和日志；
- 可用时的截图；
- 恢复尝试和恢复结果；
- 最终报告与压缩包路径。

## 四、Gawain 项目应该负责的工作

Gawain 仍然需要自己的业务测试，但这些内容不应回写到公共平台：

| Gawain 专属内容 | 原因 |
|---|---|
| Gawain 角色、卡牌、遗物、专属事件和专属调试命令 | 其他 Mod 不具备这些对象，写入平台会造成错误默认值 |
| Gawain 卡牌 ID 与运行时 ID 的转换 | 这是 Gawain 的命名约定，不是游戏通用规则 |
| Gawain 初始牌组、专属遗物和数值断言 | 属于产品功能验收，不属于平台导航 |
| Gawain 本地化 Key、文本、资源和打包断言 | 属于项目交付质量，不属于通用游戏控制 |
| Gawain M1-M7 的用例编排和业务通过标准 | 属于项目回归范围，平台只负责可靠执行 |
| Gawain 特有的构建、发布目录和 Mod 名称 | 应放在项目配置或项目测试入口 |
| “选择 Gawain”这样的自然语言别名 | 应由项目配置提供映射；平台只接受最终角色标识或通用选择动作 |

截至 2026-07-20（P2-1），上表所列 Gawain 专属规则已全部迁出平台：`test_agent_runner` 的角色、初始牌组、初始遗物与本地化前缀断言改由项目测试计划 YAML 提供；自然语言角色别名（含"选择魔网共鸣"等机制词汇）与卡牌 ID 前缀、种子调试命令改由项目扩展配置（`project_extension` / `STS2_PROJECT__*`）提供；平台仓库不再保留 Gawain 生成测试文件。迁移清单与证据见 `docs/p2/2026-07-20-p2-1-gawain-migration-inventory.md`。

## 六、统一目标场景能力（2026-07-16）

平台公共目标执行器接受 `character_id`、`target_scene`、`route_policy`、`combat_mode`、`timeout` 和 `evidence`。目标场景包括主菜单、角色选择、地图、事件、战斗、营火、商店、宝箱、卡牌奖励和下一章。

目标场景由同一组公共处理能力组成：事件按第一个未锁定选项推进；地图按真实横向坐标选择最左可走节点；战斗在 `traversal` 模式公开 `win_combat` 时使用平台级快速结束命令，否则按第一张当前可合法操作的牌或结束回合推进；`death` 模式只结束回合直到真实 `GAME_OVER`（角色死亡测试）。`journey=card_test` 通过调试控制台把指定 `card_id` 加入手牌并真实打出，平台只断言入手、出牌和状态变化等通用事实（2026-07-17）。奖励、营火、商店和宝箱各自处理完必要步骤后才返回地图。整章遍历只是 `target_scene=NEXT_ACT` 的组合调用。

运行记录会持续保存章节、楼层、页面、房间、最后动作和最后可观察变化；每次地图选择、页面切换、失败和恢复都会进入机器可读轨迹。目标不可达、动作无进展、控制入口失联和证据采集失败均不得被普通超时掩盖。

## 五、其他 Agent 的接入方式

### 推荐方式：MCP 持久任务

适用于 ChatGPT、WorkBuddy、ClaudeCode、OpenClaw、Hermes 等能调用 MCP 的 Agent：

1. 调用 `capabilities`，确认平台支持的任务状态和旅程；
2. 调用 `submit_run`，提交项目、套件、超时、证据级别和幂等键；
3. 保存返回的 `run_id`；
4. 按需调用 `get_run` 查询；
5. 超时或不再需要时调用 `cancel_run`；
6. 中断后调用 `resume_run`；
7. 任务结束后调用 `get_report`。

### 兼容方式：CLI JSON

不支持 MCP 的 Agent 使用命令行：

```bash
autotest capabilities --json
autotest run --project gawain --suite m1-m7 --detach --idempotency-key gawain-m1-m7-20260715
autotest status <run_id> --json
autotest resume <run_id>
autotest report <run_id>
```

Agent 只需要解析标准输出中的 JSON，不需要理解内部模块或目录结构。

## 六、验收门槛

### 当前落地状态（2026-07-16）

平台公共任务服务、CLI/MCP 双入口、幂等、单游戏排队、取消、恢复、证据读取和跨入口契约测试已经落地；全量单元回归为 `1500 passed`，集成回归为 `30 passed, 5 skipped`。

WorkBuddy 的共享回归记录进一步证明：Gawain 的实际驱动已经复用 `AgentAdapter` 和公共导航入口，战后卡牌选择连续 7 轮回到地图的修复进入了平台公共代码。但该记录也明确，崩溃重启、phantom combat 和旅行挂起看门狗仍放在任务专用驱动脚本中；因此这部分应继续收敛到平台生命周期管理器，不能把一次 Gawain 任务通过当成平台已完成。

跨 Agent 的协议级验收见 [`docs/cross-agent-acceptance.md`](cross-agent-acceptance.md)。具体客户端的真实接入仍需逐一留下外部实测凭证。

平台能力只有同时满足以下门槛，才可称为“稳定支持全自动回归”：

1. 同一请求重复提交不会生成两个游戏任务；
2. 控制端退出后任务仍能继续，且可以查询；
3. 同时提交多个任务时只有一个任务真正操作游戏；
4. 新局、旧局、开局事件、卡包、选牌、战后奖励和首战入口都有独立的可重复测试；
5. 地图旅行状态必须发生实际变化，不能只因为页面仍显示 MAP 就判定通过；
6. phantom combat、旅行挂起、接口失联至少各有一条故障注入测试；
7. 每次失败都能区分项目失败、平台失败和环境阻塞；
8. 每次运行都有 `run_id`、状态、原始证据和最终报告；
9. 协议级测试已覆盖 MCP 和 CLI；ChatGPT、WorkBuddy、ClaudeCode、OpenClaw、Hermes 仍需各自在真实 Agent 环境完成一次“提交—查询—取报告”验收；
10. 公共平台测试不依赖 Gawain 卡牌、角色或专属调试命令。

## 七、实施顺序

### 第一阶段：统一入口和任务可靠性

完成任务契约、持久化、幂等、单游戏排队、取消、恢复和标准状态查询。目标是“任何 Agent 都能可靠地提交和取回一次任务”。

### 第二阶段：生命周期和通用旅程

完成新局、旧局、开局事件、卡包、选牌、战后奖励、稳定地图和首战入口，增加异常局恢复及故障注入测试。

### 第三阶段：证据和报告闭环

统一每个任务的证据目录、截图/日志/状态快照、JUnit/JSON/HTML 报告和压缩包，并让 `get_report` 返回可直接消费的失败信息。

### 第四阶段：项目扩展边界

把 Gawain 角色映射、卡牌 ID、专属调试命令、M1-M7 断言和构建部署参数迁移到项目配置或 Gawain 专属测试包，平台保留通用动作和通用状态。

### 第五阶段：多 Agent 互操作验收

先用同一个任务契约验证 MCP 客户端和 CLI 客户端，再在 ChatGPT、WorkBuddy、ClaudeCode、OpenClaw、Hermes 中各完成一次真实提交—查询—取报告。验收重点是结果一致，而不是某个 Agent 的提示词或操作习惯。
