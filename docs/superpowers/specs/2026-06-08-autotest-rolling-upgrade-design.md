# STS2-AUTOTEST 统一滚动升级 — 设计规格

> 日期：2026-06-08
> 来源：版本治理讨论
> 状态：设计已确认，待 writing-plans

## 概述

`STS2-AUTOTEST` 当前仍处于能力快速演进阶段，暂不引入项目级 lockfile、launcher 或版本分发器。现阶段采用**统一滚动升级**策略：

- 工作区内只维护一个当前生效的 `STS2-AUTOTEST` 版本
- 所有接入的 mod 项目默认直接使用当前版本
- autotest 升级后，新能力立即对所有 mod 项目生效
- 如果升级导致旧项目运行异常，优先由 autotest 平台侧补兼容，而不是要求各 mod 项目各自锁版本或回退

该设计目标是先降低运维复杂度，保障新能力可快速覆盖所有项目；等 autotest 经过更多版本迭代、能力面趋于稳定后，再评估是否升级到更正式的版本治理模型。

## 设计决策

| 决策点 | 选择 |
|--------|------|
| 当前版本治理路线 | 路线 1：统一滚动升级 |
| 项目是否锁定 autotest 版本 | 否 |
| 升级后新功能生效范围 | 所有已接入 mod 项目立即生效 |
| 旧项目兼容责任 | autotest 平台侧优先负责 |
| breaking change 策略 | 允许演进，但要提供兼容修复、迁移适配或明确废弃说明 |
| 当前阶段是否引入 launcher/lockfile | 否，延后到后续稳定阶段再评估 |

## 目标

本阶段只解决以下三个问题：

1. 明确 `STS2-AUTOTEST` 升级后如何作用到所有 mod 项目
2. 提高版本可观测性，确保每份测试产物都能追溯到具体 autotest 版本
3. 约定升级引发兼容性问题时的责任归属和处理方式

本阶段**不包含**：

- 项目级版本锁定
- 多版本并存安装
- launcher / 版本分发器
- 自动下载指定版本 autotest

## 运行模型

### 1. 单一生效版本

工作区内任一时刻只认一个当前生效版本，版本源头为 [src/sts2_autotest/__init__.py](/Users/chris/STS2-WORKSPACE/STS2-AUTOTEST/src/sts2_autotest/__init__.py:1) 中的 `__version__`。

无论通过 CLI、pytest plugin、MCP service 还是脚本入口触发测试，运行时都应读取同一个版本值并写入产物。

### 2. 全项目直接跟随

所有已接入的 mod 项目默认直接依赖“当前安装的 autotest”，不在各自仓库保存固定 autotest 版本声明。

这意味着：

- autotest 升级后，所有 mod 项目下一次运行时自动使用最新版能力
- mod 项目无需主动执行版本切换操作
- 平台升级收益最大化，但兼容性压力集中到 autotest 仓库自身

### 3. 平台侧承担兼容

如果 autotest 升级后导致旧项目测试流程、测试计划格式、报告读取逻辑或集成入口失效，默认视为 autotest 平台兼容性问题。

处理顺序如下：

1. 优先补平台兼容层
2. 其次增加迁移适配逻辑
3. 最后才考虑宣布废弃旧行为，并提供明确迁移说明

除非旧行为已经无法维护，否则不应把升级适配责任下放到每个 mod 项目。

## 可观测性要求

### 1. 版本写入测试产物

以下输出应明确记录 `autotest version`：

- `summary.json`
- Markdown 测试报告
- 证据包元数据
- 必要时的 MCP / CLI 返回摘要

目标是让任何一次测试结果都能回答：

- 这是哪个 mod 项目跑出来的
- 这是哪次 run
- 这是由哪个 autotest 版本执行的

### 2. 升级问题可追溯

当某个项目在 autotest 升级后开始失败或阻塞时，应能快速区分：

- 业务逻辑回归
- 测试用例本身缺陷
- autotest 平台升级引入的兼容性问题

因此版本信息不能只出现在控制台，而必须进入最终产物。

## 兼容性分类

### 1. 结果分类原则

升级引发的问题不应默认混入业务失败。

建议将“平台升级导致旧项目暂时不可运行”归类为平台兼容性阻塞，语义上接近：

- `BLOCKED`
- 原因：`autotest_compatibility_blocked`

这样报告消费方能明确识别：

- 不是被测 mod 功能失败
- 是 autotest 平台升级后的兼容性问题

### 2. 平台契约稳定面

内部实现允许快速迭代，但以下对外契约应尽量稳定：

- 测试计划格式
- 报告 schema
- CLI 命令语义
- MCP tool 的入参与返回结构

也就是说，可以改内部 orchestration、日志采集、证据打包实现，但对外接口应避免频繁破坏。

## 发布与变更约定

### 1. 每次升级的最低要求

凡是可能影响既有 mod 项目的 autotest 升级，至少应提供简短升级说明，包含：

- 影响面
- 是否自动兼容
- 若不兼容，临时恢复方式
- 后续修复或迁移计划

### 2. breaking change 处理原则

允许 breaking change 存在，但不允许“无说明、无兜底、无归因”。

若必须引入 breaking change，应至少满足以下之一：

- 发布时已包含兼容层
- 发布时已包含迁移逻辑
- 发布说明中明确列出影响对象、替代方案和修复路径

## 推荐的近期落地点

### 1. 版本可观测性

将 `__version__` 接入所有核心测试产物，优先覆盖报告与摘要文件。

### 2. 兼容性阻塞状态

为“autotest 升级导致旧项目不可运行”定义统一状态和原因码，避免误报为业务失败。

### 3. 升级说明模板

建立一份最小升级说明规范，要求任何影响旧项目的版本迭代都输出一致格式的说明。

## 后续演进边界

当 autotest 功能趋于完整、跨项目使用场景稳定后，再评估是否从统一滚动升级演进到更正式的治理模型，例如：

- launcher + 项目 lockfile
- 项目声明兼容版本范围
- 多版本并存与按项目选择运行版本

在当前阶段，不提前引入这些机制，以免给快速迭代增加额外运维负担。
