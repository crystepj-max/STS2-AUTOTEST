# P2 通用测试平台收口交接

日期：2026-07-20  
接手对象：Kimi  
执行顺序：先完成 P2-1，再完成 P2-2  

## 一、事情背景

STS2-AUTOTEST 已经初步具备最终通用能力：调用方给出合法角色标识和目标场景后，平台会在限定时间内完成操作并返回可验证结果；无法完成时，会说明最后成功位置、失败原因和证据位置，而不是只返回超时。

这项判断已有两组正式成果支持：

- P0 目标场景能力已通过：十类目标场景、完整第一章、Boss、Boss 奖励、第二章入口事件和第二章稳定地图均有真实任务凭证；IRONCLAD 与 SILENT 使用同一套规则完成验证。
- P1 任务生命周期已通过：能力查询、提交、查询、取消、恢复和取报告六项公共操作均完成真实验收；重复提交不会重复启动任务，取消后能清理旧局，恢复后能继续执行，失败时不会假报成功。

权威基线：

- `docs/handoff/2026-07-17-goal-scene-p0-final.md`
- `docs/handoff/2026-07-19-p1-v11-fix-handoff.md`
- `docs/baselines/2026-07-20-p1-v11-cross-agent.md`
- `docs/platform-capability-inventory.md`
- `docs/cross-agent-acceptance.md`

因此，本轮 P2 **不再重做**新局、旧局、事件、奖励、地图、战斗、Boss、整章、取消或恢复能力。P2 要解决的是最后两项产品化缺口：

1. 新通用流程已经与角色和 Mod 无关，但平台其他历史区域仍残留 Gawain 专属默认规则。
2. 公共任务入口已经证明客户端无关，但 WorkBuddy、Claude Code、OpenClaw、Hermes 等外部 Agent 尚未全部留下独立真实接入凭证。

## 二、总目标

完成后，STS2-AUTOTEST 应达到下面的对外承诺：

> 任意 Agent 只需提供合法角色标识、目标场景和任务参数，就能通过同一公共入口提交、查询、中断、恢复并取得报告；平台不会因为调用方是谁、角色叫什么或使用哪个 Mod 而切换隐藏规则。

本轮不以“新增更多游戏玩法”为目标，而以“消除隐性依赖、完成真实外部复用证明”为目标。

# P2-1：清除项目专属默认规则

## 1. 背景

P0 的目标场景执行路径已经不依赖 Gawain，但平台历史功能中仍可看到以下专属内容：

- 把“Gawain”直接转换为固定角色标识；
- 把某种项目卡牌写法直接转换为 Gawain 运行时名称；
- 平台直接调用 Gawain 专属调试指令；
- 构建、部署、冒烟和自然语言测试中存在 Gawain 的固定默认值；
- 一部分检查数据把 Gawain 示例当成默认业务事实，而不是普通样例。

这些残留不一定影响当前整章流程，但会产生产品风险：新 Mod 看似接入通用平台，实际可能在角色解析、卡牌处理、构建部署或自然语言测试阶段触发 Gawain 的历史规则。

## 2. 目标

让公共平台只认识通用概念：角色标识、卡牌标识、项目配置、目标场景和可执行操作。

Gawain 的角色别名、卡牌命名、专属调试指令、构建方式、发布目录和 M1-M7 通过标准，应由 Gawain 项目自己提供，不能继续作为平台默认行为。

## 3. 建议方案

### 第一步：做完整清单，不直接批量删除

把所有 Gawain 相关内容分成三类：

1. **必须迁出**：会在真实任务中改变角色选择、卡牌处理、调试操作、构建部署或通过标准的规则。
2. **可以保留为中性样例**：只用于证明平台能处理任意字符串或任意 Mod 数据，不会改变真实任务行为的测试样本。
3. **仅属历史文档**：明确标注为案例或历史记录，不会被平台执行。

不要用“全仓搜索后全部删除”的方式处理。目标是删除隐藏默认规则，不是抹掉历史证据。

### 第二步：为项目专属信息建立明确接收位置

优先采用“两边同时迁移”的方式：

- STS2-AUTOTEST 保留通用入口和通用执行规则；
- STS2-GAWAIN 保存 Gawain 的角色别名、卡牌映射、专属指令、构建部署参数和业务断言；
- Gawain 通过项目配置或项目测试包把这些信息作为任务输入交给平台。

如果本轮没有 STS2-GAWAIN 的修改权限，不要直接删除现有行为。先完成迁移清单和平台接收规则，并把“需要 Gawain 仓库承接的内容”列成阻塞项，等待获得权限后再完成切换。

### 第三步：用三个不同对象证明没有隐藏默认值

至少使用：

- 一个原游戏角色；
- 第二个不同的原游戏角色；
- 一个 Mod 角色。

三者都通过相同公共入口完成短目标；至少一个角色再完成整章目标。三个对象之间不得修改平台规则，只允许更换任务输入或项目配置。

### 第四步：保护既有成果

迁移后必须复跑 P0 和 P1 的关键验收，确认去除专属默认值没有破坏：

- 十类目标场景；
- 第一章到第二章；
- 重复提交防重；
- 局内取消；
- 干净恢复；
- 报告和证据包读取。

## 4. 验收标准

以下条件必须全部满足：

1. 公共平台的真实任务规则中，不再存在 Gawain 角色、卡牌、遗物、事件、调试指令、构建目录或 M1-M7 标准的固定默认值。
2. Gawain 专属内容有明确归属：已迁入 Gawain 项目，或因权限不足形成清晰阻塞清单；不得静默删除后导致 Gawain 回归失效。
3. 原游戏两个不同角色使用同一套平台规则完成短目标，过程中不修改平台。
4. 一个 Mod 角色通过项目输入完成同类短目标，平台不增加该角色专属判断。
5. 至少一次完整整章任务通过，证明迁移没有破坏 P0 能力。
6. 至少一次“提交—取消—清理—恢复—取报告”通过，证明迁移没有破坏 P1 能力。
7. 失败时仍能区分产品失败、平台失败和环境阻塞，并保留最后状态、截图、日志和报告。
8. 自动检查全部通过；若有环境跳过，必须逐项说明，不得把跳过写成通过。
9. 文档中的平台边界与实际行为一致，不再一边声称通用、一边保留专属默认规则。

## 5. 不属于本任务的内容

- 不重写已经通过的目标场景执行流程；
- 不为 Gawain 增加新玩法测试；
- 不扩大到覆盖率报表、多人同时操作游戏或视觉语义判断；
- 不删除历史报告和失败证据；
- 不用另一个项目专属规则替换 Gawain 专属规则。

## 6. 交付物

- 一份专属内容迁移清单，说明每项内容的原位置、新归属和处理结果；
- 平台侧修改与对应检查；
- 如有权限，Gawain 项目侧接收修改与回归结果；
- 三角色短目标结果；
- 一次整章结果；
- 一次完整取消与恢复结果；
- 最终结论：PASSED / PARTIAL / BLOCKED，并附证据位置。

# P2-2：真实多 Agent 接入验收与交付

## 1. 背景

P1 已证明公共任务入口本身可以完成完整生命周期，但“入口对所有 Agent 都一致”与“每个 Agent 已经真实接入并能独立完成任务”不是同一件事。

当前已知情况：

- ChatGPT/Codex 已有真实公共任务记录；
- Claude Code 已参与 P1 的真实验收；
- WorkBuddy 的历史 M1-M7 回归证明它使用过部分公共能力，但主要仍是任务专用驱动，不能替代当前六项公共操作的完整验收；
- OpenClaw、Hermes 尚缺少正式的独立接入凭证；
- 不支持公共工具调用的 Agent 可以使用同一任务入口的命令行 JSON 方式（即：通过标准机器可读文本完成同样操作），但结果含义必须一致。

WorkBuddy 历史参考：

https://codebuddy.work/agents/tasks/share/xW5Z9GzzGk?platform=workbuddy

## 2. 目标

让 ChatGPT/Codex、WorkBuddy、Claude Code、OpenClaw、Hermes 各自在自己的真实环境中完成同一套最小流程，并留下可复核证据。

Agent 只负责：

- 查看平台支持什么；
- 提交任务并保存任务编号；
- 查询任务进度；
- 必要时取消或恢复；
- 获取最终报告。

Agent 不得自己重写新局、事件、奖励、地图、战斗、恢复或证据采集逻辑。

## 3. 建议方案

### 第一步：提供一份客户端无关的最短使用说明

使用说明只描述六项公共操作：

- `capabilities`：查看平台支持的任务；
- `submit_run`：提交任务；
- `get_run`：查询进度；
- `cancel_run`：取消任务；
- `resume_run`：恢复任务；
- `get_report`：获取结果和证据。

说明中提供两套等价示例：可直接调用公共工具的 Agent 使用公共工具；不能直接调用的 Agent 使用机器可读命令。两种方式不得产生不同的状态名称或报告结构。

### 第二步：所有 Agent 先跑同一个短目标

建议统一使用“新局到稳定地图”的短目标，减少每个 Agent 的时间成本，同时足以验证：

- 参数提交；
- 新局与角色选择；
- 事件处理；
- 进度查询；
- 最终报告；
- 截图、日志和状态证据。

所有 Agent 使用同一角色、同一目标、同一路线规则和同一证据等级。每次任务使用独立防重键，不允许复用其他 Agent 的任务编号冒充自己的验收。

### 第三步：每个 Agent 补一次中断恢复验证

每个 Agent 至少完成一次下列任一场景：

- 任务执行中主动取消，再恢复成新任务；
- Agent 连接中断后，使用原任务编号重新查询并取得报告。

这一步用于证明 Agent 退出或网络中断不会让测试结果丢失。

### 第四步：形成统一验收矩阵

每个 Agent 单独记录：

- 平台能力版本；
- 提交参数；
- 防重键；
- 任务编号；
- 从排队到终态的状态变化；
- 取消或断线恢复记录；
- 最终结果；
- 报告与证据包位置；
- 是否使用了 Agent 专属脚本或人工点击。

若某个 Agent 无法接入，必须说明是账号权限、连接配置、环境不可用还是平台兼容问题，不能统一写成“调用失败”。

## 4. 验收标准

以下条件必须全部满足：

1. ChatGPT/Codex、WorkBuddy、Claude Code、OpenClaw、Hermes 五类 Agent 均有独立真实任务编号和原始调用记录。
2. 五类 Agent 均完成能力查询、任务提交、进度查询和最终报告读取。
3. 五类 Agent 均证明一次防重提交：相同防重键重复提交返回同一任务编号，不会启动第二局游戏。
4. 五类 Agent 均完成一次取消恢复或断线后重查；不得只验证正常成功路径。
5. 五类 Agent 的任务状态、失败分类、进度字段和报告含义一致。
6. 每个成功任务都有状态轨迹、完整游戏窗口截图、游戏日志、机器报告和可读取证据包。
7. 每个失败或阻塞任务都包含最后成功位置、最近操作、失败归类和证据位置。
8. Agent 之间只允许修改接入地址、身份凭据或调用方式，不允许修改平台执行规则。
9. 不允许用人工点击、Agent 临场判断或任务专用长脚本帮助某个 Agent 通过。
10. 最终输出一张五类 Agent 验收矩阵；未通过者必须标记 PARTIAL 或 BLOCKED，不得用平台内部检查代替真实接入。

## 5. 不属于本任务的内容

- 不要求每个 Agent 都重新跑完整第一章；短目标加中断恢复已足够证明接入。
- 不为每个 Agent 维护一套不同提示词或游戏推进脚本。
- 不修改已通过的目标场景规则来迁就某个 Agent。
- 不把 WorkBuddy 历史 M1-M7 页面直接当成本轮通过凭证。
- 不把平台内部自动检查当成外部 Agent 真实验收。

## 6. 交付物

- 一份客户端无关的最短接入说明；
- 五类 Agent 的独立原始调用记录；
- 五类 Agent 的任务与证据包；
- 一张统一验收矩阵；
- 接入失败分类与后续责任归属；
- 最终结论：每个 Agent 分别标记 VERIFIED / PARTIAL / BLOCKED。

# 三、执行顺序与停止条件

## 执行顺序

1. 完成 P2-1 专属规则迁移并通过跨角色验证。
2. 冻结平台行为，不再为单个 Agent 修改游戏推进规则。
3. 执行 P2-2 五类 Agent 真实接入验收。
4. 汇总结果，更新平台能力盘点与跨 Agent 验收状态。

## 允许停止并请求用户介入的情况

- 缺少某个 Agent 的账号、安装环境或连接权限；
- 没有权限修改 STS2-GAWAIN，导致专属规则无法安全迁移；
- Steam、游戏或公共控制入口不可用，且安全恢复方式已用尽；
- 需要改变公开任务字段或结果含义，会影响已有调用方；
- 现有成果与新验收标准发生实质冲突，需要产品决策。

任务困难、首次运行失败、运行时间较长，不属于停止理由。
