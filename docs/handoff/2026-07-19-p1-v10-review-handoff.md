# 2026-07-19 P1 跨 Agent 通用性 V10 复核交接

## 零、新接手者先读这里

你可以假设自己此前没有参与过 STS2-AUTOTEST，也没有看过 Codex、Kimi 或 WorkBuddy 的历史会话。本节用于解释：项目在解决什么问题、为什么做 P1、此前发生了什么、当前哪些结论可信。

### 1. STS2-AUTOTEST 是什么

STS2-AUTOTEST 是《杀戮尖塔 2》的公共自动化测试平台。它不负责某个角色或 Mod 的具体玩法，而是负责所有测试都会重复遇到的公共工作：

- 启动并确认游戏真正可操作；
- 清理上一局残留；
- 选择任务传入的角色；
- 处理事件、地图、战斗、奖励、商店、宝箱、营火等通用页面；
- 把任务排队、持久化、取消和恢复；
- 收集状态、截图、日志和报告；
- 在失败时区分平台问题、游戏产品问题和机器环境问题。

平台的长期目标是：

> 给平台任意合法角色标识和目标场景，平台要么在限定时间内完成并返回可验证结果，要么明确说明卡在哪一步、为什么无法继续，并提供完整证据。

平台公共能力不能依赖：

- Gawain 或其他 Mod 的规则；
- 角色名称对应的特殊分支；
- 某张卡牌、遗物或事件的业务名称；
- 某个 Agent 的临场判断；
- 人工点击帮助任务通过；
- “动作接口返回成功”但游戏状态没有变化的假成功。

### 2. P0 和 P1 分别解决什么

#### P0：目标场景和真实整章能力

P0 解决“平台能不能通用地操作游戏”。它已经完成真实验收，包括：

- 十类公共目标场景；
- 新局、角色选择、事件、地图、战斗、奖励等通用推进；
- 第一章完整遍历到第二章稳定地图；
- 第二章入口事件被观察并处理；
- 卡牌专测；
- 角色死亡专测；
- macOS 真实游戏窗口截图；
- 游戏日志、状态轨迹、报告和压缩包持久读取。

P0 最终交接位于：

`docs/handoff/2026-07-17-goal-scene-p0-final.md`

P0 证明的是“平台具有初步通用游戏操作能力”，不等于“任何外部 Agent 都能稳定使用它”。

#### P1：跨 Agent 通用性和任务生命周期

P1 解决“不同 Agent 是否可以不理解平台内部实现，只使用统一公开入口完成任务全生命周期”。

这里的 Agent 包括但不限于：

- Codex；
- WorkBuddy；
- Claude Code；
- Kimi；
- Hermes；
- OpenClaw。

P1 重点不是再次证明能走地图，而是证明：

- 不同 Agent 看到的是同一份能力契约；
- 相同请求不会重复启动游戏任务；
- 查询不会依赖提交任务的 Agent 仍在线；
- 任务可以被取消；
- 取消后不会留下污染下一任务的旧局；
- 取消任务可以创建新的恢复任务；
- 恢复任务和原任务有明确关联；
- 报告和证据在服务重启后仍可读取；
- 环境事故不会被误报成产品失败。

### 3. 外部 Agent 实际调用什么

外部 Agent 不应直接操作游戏进程、Steam、平台内部代码或证据目录。标准链路是：

```text
外部 Agent
    ↓ 公共 MCP 六操作
STS2-AUTOTEST 公共任务服务（127.0.0.1:8090）
    ↓ 创建和管理持久任务
任务执行进程
    ↓ 游戏控制接口
STS2 游戏控制服务（127.0.0.1:8080）
    ↓
真实 STS2 游戏窗口
```

任务结束后，平台把任务记录、状态、截图、日志和报告保存到 `tests/output/`。

两个端口的含义不能混淆：

- 8090 可访问，只代表公共任务服务存在；
- 8080 的健康、状态和可执行操作均可读取，才代表游戏真正可操作；
- 8090 正常但 8080 失联，应归类为环境阻塞，不能继续把任务当作正常运行。

### 4. 六个公开操作是什么

P1 的唯一公共契约包含：

1. `capabilities`：查询平台实际公开什么能力；
2. `submit_run`：提交任务，返回 `run_id`；
3. `get_run`：查询排队、运行、进度和终态；
4. `cancel_run`：取消任务；
5. `resume_run`：从可恢复任务创建新的恢复任务；
6. `get_report`：读取正式结果和证据位置。

同一任务还必须提供 `idempotency_key`。使用相同幂等键重复提交时，必须返回同一个 `run_id`，不能启动第二个游戏任务。

### 5. 本交接中的几个术语

| 术语 | 含义 |
|---|---|
| ORIG | 第一条原始任务；真实进入局内后被取消 |
| RESUME | 通过 `resume_run` 从 ORIG 创建的新任务，必须有新 run_id 和正确 `resumed_from` |
| SECOND | RESUME 完成后再次提交的独立任务，用来证明没有继承残留局面 |
| 干净主菜单 | 主菜单中没有旧局，不能出现“继续游戏”和“放弃当前游戏” |
| 受控重启 | 只结束 STS2 游戏并启动一次，再确认游戏可操作；不是重启整台机器或无限重试 |
| evidence sealed | 任务证据已经封存，报告和压缩包不应再发生不一致 |
| BLOCKED_ENVIRONMENT | Steam、游戏控制入口、图形会话或机器环境不可用，不代表游戏产品失败 |
| FAILED_PLATFORM | 平台能接触环境，但无法正确导航、恢复、判定或留证 |
| CANCELLED | 取消已完成，游戏已恢复到不污染下一任务的安全状态，证据已封存 |

### 6. 为什么发生过 WindowServer 事故

第一轮跨 Agent 真实验收在 macOS 上长时间无人值守运行。运行过程中显示器进入关闭状态，随后 WindowServer 被系统看门狗终止。游戏窗口停止渲染，8080 控制接口失去响应，任务被打断。

这次事故暴露出三个平台问题：

- 长任务没有阻止显示器和系统睡眠；
- 游戏控制入口失联和真正的产品失败没有充分区分；
- 环境崩溃后继续重试可能造成“崩溃—启动—再次崩溃”的循环。

因此后续加入了防睡眠生命周期、环境健康探测和有界恢复。此前被 WindowServer 打断的结果全部作废，不能作为 P1 成功或失败证据。

### 7. 第一轮跨 Agent 验收为什么不能直接沿用

用户曾分别让 WorkBuddy、Claude Code 和 Kimi 使用同一套提示词执行公共任务。第一轮结果没有形成三个独立、完整、可比较的闭环：

- 部分任务被 WindowServer 事故直接打断；
- 部分任务在尚未执行取消和恢复前就进入环境阻塞终态；
- 多个 Agent 共用同一个游戏会话，前一条任务的局面可能影响后一条；
- 有的报告验证了提交和查询，但没有真正执行取消、恢复和正式报告读取；
- 环境阻塞和平台恢复失败一度混在一起。

系统重启后，Kimi 重新执行仍得到 `BLOCKED_ENVIRONMENT`，原因是原任务过早终止，取消与恢复链路没有机会执行。因此 P1 后续工作从“分别要求每个 Agent 再跑一次”转向“先修平台生命周期，再用一套可重复的三柱验收证明任何 Agent 都能调用”。

这里要区分两个结论：

- Agent 是否会调用六操作，属于接入问题；
- 六操作能否在共享真实游戏上稳定完成生命周期，属于平台问题。

当前未完成的是第二项，不能继续把失败归因于某个 Agent 能力较弱。

### 8. 为什么会讨论 `return_to_menu`

跨 Agent 生命周期验收要求：一条任务取消后，下一条任务不能继承其地图、事件或战斗状态。

理想方式是：打开游戏菜单，选择放弃当前游戏，正常返回主菜单。但当前公共游戏控制入口在部分局内页面没有稳定公开这个动作，WorkBuddy 因此长期卡在 `return_to_menu` 节点。

用户随后明确接受 P1 使用降级方案：

> 直接结束 STS2 游戏进程，然后启动一次游戏，也可以达到恢复到主菜单的结果目标。

接受降级方案不等于降低结果标准。启动后如果仍存在旧局，平台必须继续放弃旧局并确认删除。最终必须是“没有继续游戏入口”的干净主菜单。

### 11. 新接手者应相信哪些信息

可信度从高到低：

1. 真实任务状态文件、压缩包内报告、状态 JSON、截图和日志；
2. 公共 `get_run` / `get_report` 的原始响应；
3. 自动检查的完整原始输出；
4. 交接文档中引用上述证据得出的结论；
5. Agent 小结或机器汇总中的单个布尔值。

当截图、状态和汇总布尔值冲突时，以原始状态和真实截图为准，不能为了沿用旧结论而忽略反例。

## 一、交接结论

当前状态：**PARTIAL，V10 不接受 PASS，需继续完成 V11 修复与真实验收。**

WorkBuddy 已经真实跑通“局内取消 → 创建恢复任务 → 恢复任务通过 → 再提交连续任务”的主要链路，三个最终任务及其证据包也真实存在。但复核发现，V10 的机器判定存在假阳性：两条取消任务的最终截图仍显示“继续游戏 / 放弃当前游戏”，说明旧局未清除，却被报告为 `clean_main_menu=true` 并判为 `CANCELLED`。

此外，当前实现无法证明“最多只重启一次”，V10 驱动也没有真正执行完整的六操作和幂等验证。因此，当前不能把 P1 标记为完成。

## 二、本阶段最终目标

P1 聚焦跨 Agent 通用性。完成后，WorkBuddy、Claude Code、Kimi、Hermes 或其他 Agent 只依赖同一套六个公开操作，即可完成：

1. 查询平台能力；
2. 提交任务；
3. 查询进度和终态；
4. 使用相同幂等键重复提交而不创建第二个任务；
5. 在任务真实进入局内后取消；
6. 平台把游戏恢复到没有旧局的干净主菜单；
7. 从取消任务创建新的恢复任务；
8. 恢复任务最终达到 `PASSED`；
9. 获取正式报告和可验证证据包；
10. 下一条独立任务不继承上一条任务的残留局面。

六个公开操作必须全部通过公共 MCP 使用：

- `capabilities`
- `submit_run`
- `get_run`
- `cancel_run`
- `resume_run`
- `get_report`

## 三、已确认的产品决策

### 1. `return_to_menu` 的 P1 处理方式

正常通过 ESC 菜单选择“放弃当前游戏”暂时降级为后续增强，不阻塞 P1。

P1 接受的正式后备方案是：

> 结束已确认的 STS2 游戏进程 → 等待进程和控制入口释放 → 只启动一次游戏 → 等待真正可操作 → 如有旧局则放弃旧局 → 确认干净主菜单。

这个后备方案是恢复手段，不是普通游戏操作。必须满足：

- 每次取消最多启动一次游戏；
- 失败后立即返回环境阻塞，禁止继续重启；
- 不能只看到主菜单画面就算完成；
- 旧局必须清除；
- 报告必须记录真实恢复动作和最终状态。

### 2. 干净主菜单的唯一完成定义

必须同时满足：

- `screen=MAIN_MENU`；
- `has_run_save=false`；
- 可执行操作中没有 `continue_run`；
- 可执行操作中没有 `abandon_run`；
- 可执行操作中存在开始新局能力；
- 最终截图与状态 JSON 一致。

只满足 `screen=MAIN_MENU` 不算完成。

### 3. WindowServer 与防睡眠

跨 Agent 长任务曾被 macOS 图形会话事故打断。平台已加入防睡眠生命周期，后续验收必须继续确认：

- 任务运行期间防睡眠已启动；
- 任务终止后没有残留防睡眠进程；
- 游戏控制入口失联时归类为环境阻塞；
- 禁止在图形会话异常后无限重启游戏。

## 五、V10 复核发现的阻塞问题

### 🔴 P0-1：干净主菜单是假阳性

ORIG 和 SECOND 报告均写入：

```text
final_screen=MAIN_MENU
clean_main_menu=true
old_run_abandoned=false
```

但最终截图显示主菜单仍有：

- “继续游戏”；
- “放弃当前游戏”。

SECOND 的直接证据：

`tests/output/run-20260719-045757-4010553c/screenshots/journey:new_run_0.jpg`

业务影响：后一条任务仍可能继承前一条任务的存档，跨 Agent 隔离没有成立。

代码根因位于：

- `src/sts2_autotest/cli/main.py` 的 `_main_menu_has_saved_run_settled`；
- `src/sts2_autotest/cli/main.py` 的 `_recover_main_menu_via_restart`。

当前流程虽然多次读取菜单状态，但只返回布尔值；最终 `clean_main_menu` 仍使用主菜单刚出现时的旧快照。因此，旧局信号稍晚出现时会漏判。

### 🔴 P0-2：取消成功只要求“到主菜单”，不要求“干净”

当前 `recovery.ok` 只依赖 `screen=MAIN_MENU`。取消收尾随后据此把任务标记为 `CANCELLED`，没有把 `clean_main_menu=true` 作为强制条件。

业务影响：平台会把“仍有残留旧局”的取消任务对外宣称为成功取消。

### 🔴 P0-3：最多启动一次没有真正实现
